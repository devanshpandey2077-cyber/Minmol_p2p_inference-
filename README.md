HiveGPT - Two phones, one forward pass
A browser-based distributed inference demo that splits an 11,040,768-parameter byte-level GPT across two phones. Both devices execute transformer layers for every generated byte, connected through a direct WebRTC DataChannel.

Open the live demo
-https://github.com/devanshpandey2077-cyber/Minmol_p2p_inference-/blob/main/README.md


This repository preserves the deployed two-phone Host/Join version. It includes the app, both exported weight halves, the weight manifest, the PyTorch reference outputs, the exporter, and the existing verification suite.
The model uses untrained seed-42 weights. It demonstrates distributed transformer execution. Its random byte output, often displayed with replacement characters, is not meaningful chatbot text.

Features
- CPU inference using JavaScript and FP32 arrays in a Web Worker.
- Six transformer blocks split evenly across Phone A and Phone B.
- Only the assigned weight half loads in normal Host/Join mode.
- Direct peer exchange of activations, generated bytes, and run controls.
- Manual offer/answer pairing with animated QR frames or text fallback.
- Generated byte arrays, FNV-1a checksums, throughput, compute times, and response RTT.
- A fixed 128-byte benchmark and an explicit browser self-test.
- App and weight caching for offline use over an active local network.
Phones need no package installation or browser flags. The inference kernels use no WebGPU, WebGL, WASM dependency, SharedArrayBuffer, or parallel compute threads. The browser manages a worker for inference, separate from shared-memory multithreading.

A sends a 384-element activation vector after block 2. B finishes the forward pass and returns a byte. A feeds that byte into the next step. Prompt bytes also traverse both devices one at a time.
Run on two phones
1. Put both phones on the same Wi-Fi or hotspot that allows devices to communicate.
2. Open the HTTPS demo on both phones. Keep both tabs visible and screens awake.
3. Choose Host (Phone A) on A and Join (Phone B) on B. Wait for each weight half to load and verify.
4. A taps Create offer. B scans all cycling offer QR frames, or pastes A's complete pairing text and taps Use pasted text.
5. B creates an answer. Scan all answer frames on A, or paste B's complete answer on A.
6. Wait for both halves to report ready, then enter a prompt on A and generate.
7. Use temperature 0 for greedy decoding. Benchmark uses Hello and exactly 128 generated bytes.
Pairing requires the offer and answer in this version. Room-code signaling and one-scan pairing are not implemented.

The context limit counts UTF-8 bytes: prompt_byte_count + new_byte_count - 1 <= 512. An empty prompt is rejected. Non-ASCII characters may occupy multiple bytes.
Run from the repository
The checked-in model halves and reference files are ready to use. Re-exporting weights is optional.
Desktop development
With Python available, serve the repository root:
python -m http.server 8000
Open http://localhost:8000 on the same computer. Avoid opening index.html as a local file: the app uses workers, fetch, and service-worker APIs. For phones, use HTTPS hosting. A laptop's plain HTTP LAN address does not provide the secure context required for camera and service-worker features.
Static HTTPS deployment
No build command or backend is required. Publish these nine files together:
App files	Model / reference files
index.html, app.js, worker.js	part_a.bin, part_b.bin
qr.js, sw.js	weights_manifest.json, reference.json


For Netlify manual deployment, put these files in a folder and upload the folder. For a Git-linked static deployment, publish the repository root and leave the build command empty. .nojekyll is included for optional GitHub Pages hosting.
Verify correctness
With Node.js 20 or newer, run the existing dependency-free suite from the repository root:
node verify.mjs
It checks greedy byte equality against the supplied PyTorch reference, first-block activation error, split generation, the benchmark, role-specific downloads, QR correction/decoding, signaling round trips, and two controllers using an in-memory binary transport.

Open the browser self-test to test a target browser. This diagnostic intentionally loads both halves on one device. Reload without ?selftest=1 before normal two-phone use.

Network and offline use
The static host serves code, the manifest, and weights, and can see ordinary download requests. Prompt bytes, activations, and generated bytes travel through the peer DataChannel. The app has no server inference endpoint, external signaling API, or telemetry.

The peer configuration uses iceServers: [], with no STUN or TURN. Devices need a network that permits direct communication. Guest Wi-Fi, client isolation, VPNs, or hotspot peer restrictions can prevent pairing. The ICE diagnostic reports selected candidate types and rejects relay candidates.

Once both phones have cached the app and their weights, disconnect the router's WAN while keeping Wi-Fi/LAN active to test offline generation. Do not disable the local network carrying WebRTC. Private browsing, storage limits, or browser eviction can remove caches. After updating weights, clear site data on both phones to avoid mixing cached manifests and binaries.
Optional export
The included export records PyTorch 2.15.0+cpu. Keep the committed binaries for the exact supplied model; different PyTorch versions can change initialization or reference numerics.

On a development computer with Python 3.10 or newer:
python -m venv .venv
Activate with .venv\Scripts\Activate.ps1 in Windows PowerShell, or source .venv/bin/activate on macOS/Linux. Then:
python -m pip install -r requirements-export.txt
python export_weights.py --out export --prompt "Hello" --n 32
Using export/ preserves the supplied assets. The exporter writes both halves, weights.bin, the manifest, and the reference. Treat them as one matched set and rerun verification after replacing any model assets. weights.bin duplicates the concatenated halves and is never requested by the app, so it is not committed.

Limits
This release supports two devices and one generation stream. Scalar JavaScript throughput depends on CPU, thermals, foreground scheduling, and local network latency. Response RTT includes downstream compute. Positive-temperature sampling runs on B. Floating-point differences can affect close argmax decisions; run the self-test on each target phone. Desktop tests do not establish physical iOS/Android ICE, camera compatibility, or device throughput.
